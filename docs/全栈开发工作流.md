# 全栈开发工作流 — AI 协作版 v2

> 2026-06-18 | 综合 GitHub Spec Kit、AWS Kiro、Notion 工作流、Agentic Engineering Methodology、Vibe Coding 最佳实践。以后所有项目按这个来。

---

## 核心理念

```
业内共识 2026：

"AI 编程失败不是因为模型不够强——是因为意图、上下文和验证没对齐。"
                                        —— Spec-Driven Development 论文

"规划占 50% 时间，实施占 50%。规划比写代码重要 2-3 倍。"
                                        —— Agentic Engineering Methodology

"Spec 不再是脚手架——它是治理 AI Agent 的长期版本化契约。"
                                        —— Mitch Ashley, Futurum Group
```

**我们的定位**：SDD 成熟度 Level 2（Spec-Anchored）。Spec 驱动开发，AI 按 Spec 实现，Spec 提交到仓库。

---

## 推荐技术栈

```
前端:   React + TypeScript + Tailwind CSS + shadcn/ui + Vite
后端:   Python + FastAPI（新）或 Flask（已有）
数据:   SQLite → PostgreSQL（Supabase 托管）
校验:   Pydantic（后端）+ Zod（前端，需要时）
AI:     Claude Code（主力）+ Playwright（视觉验证）
部署:   Vercel（前端）+ VPS/Railway（后端）
```

**为什么这个栈**：shadcn/ui 源码在项目里，AI 能读能改，不是 `node_modules` 黑盒。TypeScript + Pydantic 给 AI 强约束。Tailwind 让 AI 用语义类名而不是猜色值。

---

## 大流程（6 阶段）

```
阶段 0: Spec & 架构（不写代码）
   ↓
阶段 1: 数据模型 & API 设计（后端先行，写文档）
   ↓
阶段 2: 后端实现（逐端点 curl 验证）
   ↓
阶段 3: 前端实现（自底向上，逐组件截图）
   ↓
阶段 4: 联调 & E2E（Playwright 核心流程）
   ↓
阶段 5: 视觉打磨（截图闭环 AI 自己看）
   ↓
阶段 6: 验证门禁 & 部署
```

**每阶段的内部循环**（Vibe Coding Loop）：

```
Spec → AI 生成 → 人审查 → AI 自审 → 修正 → 门控通过 → 下一批
```

## 阶段 0：Spec & 架构

**目标**：写出 AI 能精确执行的 Spec。业内共识——**不写 Spec 不动代码**。

### 0A. 项目 Spec（README 级别）

```markdown
# 项目名称
一句话描述。

## 用户故事
- 作为[角色]，我想[做什么]，以便[为什么]

## 功能范围
- 必须做: [列表]
- 不做: [列表]
- 以后做: [列表]

## 技术选型
前端: [框架 + 组件库]
后端: [框架 + 数据库]
部署: [方案]

## 验收标准
1. [可验证的条件]
2. [可验证的条件]
```

### 0B. 架构图

画出数据流向：用户 → 前端 → API → 后端 → 数据库 → 返回。

### 0C. Spec 提交到仓库

```
docs/
├── spec.md           ← 项目 Spec（git 版本控制）
├── architecture.md   ← 架构决策
└── api-design.md     ← 下阶段产出
```

**AI 协作**（参考 GitHub Spec Kit 模式）：
```
"我要做 [项目描述]。先不写代码，帮我写出完整 Spec：
1. 用户故事 2. 功能范围（含边界） 3. 技术选型建议 4. 验收标准
输出为 docs/spec.md，等我确认后再进入下一阶段。"
```

**门控**：Spec 写进 `docs/spec.md`，人确认 → 通过。不写 Spec 不写代码。

## 阶段 1：数据模型 & API 设计

**目标**：后端先行。Schema + API 文档定死，前后端才能并行开工。

### 1A. 数据库 Schema

```sql
-- 用 ASCII 表格确认，再生成 SQL
CREATE TABLE costs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  model TEXT NOT NULL,
  in_tokens INTEGER NOT NULL DEFAULT 0,
  out_tokens INTEGER NOT NULL DEFAULT 0,
  cost_usd REAL NOT NULL DEFAULT 0,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

### 1B. API 端点文档

每个端点写清楚：

```
POST /api/chat
  说明: 发送消息，返回 SSE 流式响应
  请求: { task: string, model?: string, engine?: "claude"|"codex", session_id?: string }
  响应: SSE 流
    event: content  → { content: string }
    event: done     → { cost: number, tokens: {in,out}, model: string, session_id: string }
    event: error    → { error: string }
  错误: 400 参数缺失 | 402 预算超限 | 500 引擎异常
```

### 1C. 数据流图（复杂项目用）

```
用户输入 → [前端校验] → POST /api/chat → [后端校验] → ClaudeSession
    → SSE 流 → [前端渲染] → 费用入 cost.db
```

**AI 协作**：
```
"根据 docs/spec.md 的功能需求，设计数据库 Schema 和 API 端点。
先列出所有表（ASCII 格式）和所有端点（方法+路径+请求/响应），
等我确认后再生成代码。"
```

**门控**：Schema + API 文档人看得懂 → 通过。

## 阶段 2：后端实现

**目标**：每个 API 端点可用 curl 调通。

### 2A. 项目结构

```
backend/
├── main.py           ← 入口，路由注册
├── models.py         ← SQLAlchemy/Pydantic 模型
├── routes/           ← 每个文件 1-2 个端点
├── services/         ← 业务逻辑（与路由分离）
├── migrations/       ← 数据库迁移脚本
└── tests/
```

### 2B. 逐端点实现（一次只做一个端点）

```
循环（每个端点）:
  AI 生成路由 + Service → py_compile 检查 → curl 验证 → AI 自审 → 下一个
```

**AI 自审**（业内标准做法——AI 平均能发现自身 2-3 个 bug）：
```
"检查你刚写的代码:
- 输入校验完整吗（类型、长度、范围）？
- 错误处理是否一致（不用 console.log，用 log.error）？
- 数据库查询有 N+1 问题吗？
- 有硬编码密钥或 URL 吗？
发现问题直接修。"
```

### 2C. curl 验证（每个端点）

```bash
# 成功
curl -X POST http://localhost:8800/api/chat \
  -H "Content-Type: application/json" \
  -d '{"task":"hello","model":"deepseek-v4-flash"}'

# 错误
curl -X POST http://localhost:8800/api/chat \
  -H "Content-Type: application/json" \
  -d '{}'
# 预期: HTTP 400 + {"error":"请求为空"}
```

### 2D. 数据库迁移

不用 `ALTER TABLE` 热修。用迁移脚本：

```python
# migrations/002_add_cache_fields.py
def up(db): db.execute("ALTER TABLE costs ADD COLUMN cache_read INTEGER DEFAULT 0")
def down(db): db.execute("ALTER TABLE costs DROP COLUMN cache_read")  # 正式环境不执行
```

**AI 协作**：
```
"实现 POST /api/chat。按 api-design.md 的格式。
用 Flask/FastAPI + 已有的 ClaudeSession。
先写路由，再写 curl 验证命令，我跑通后继续下一个端点。"
```

**门控**：每个端点 curl 通过 + AI 自审通过 + 迁移脚本可回滚 → 通过。

## 阶段 3：前端实现

**目标**：页面能渲染，能调通后端。

### 3A. 搭骨架

```bash
npx create-vite webui-v2 --template react-ts
cd webui-v2
npm install tailwindcss @tailwindcss/vite
npx shadcn@latest init
npx shadcn@latest add button card dialog input dropdown-menu tabs toast
```

配 Vite proxy → 后端：
```ts
// vite.config.ts
export default defineConfig({
  server: { proxy: { '/api': 'http://localhost:8800' } }
})
```

### 3B. 画组件树（最重要的一步）

**不写代码，先画树**。从页面根节点逐层拆分：

```
App
├── Sidebar
│   ├── ConversationList
│   ├── AgentList → AgentCard (×N)
│   └── MemoryPanel
├── MainArea
│   ├── Header
│   └── PanelGrid
│       └── ChatPanel (×N)
│           ├── PanelBar
│           ├── MessageList → MessageBubble (×N)
│           ├── PipelineBar
│           └── InputArea
└── Overlays
    ├── Dashboard → CostPanel / ContextPanel / ...
    ├── Settings → ThemeSelector / ApiKeyForm / ...
    └── CommandPalette
```

**规则**：每个节点 = 一个 `.tsx` 文件。超过 200 行继续拆。

### 3C. 逐组件实现（自底向上，叶子→根）

```
第 1 轮: AgentCard, MessageBubble, CostKpi           ← 叶子组件
第 2 轮: AgentList, MessageList, CostPanel            ← 用第 1 轮组件
第 3 轮: Sidebar, ChatPanel, Dashboard                ← 用第 2 轮组件
第 4 轮: App（路由 + 布局）                           ← 组装所有
```

**业内关键规则——批次约束**：AI 一次生成 200 行比生成 50 行错误率高 3-5 倍。**每批只做一件事。**

**每个组件的标准循环**：
```
AI 写组件（50-150 行）→ npm run build → AI 自审 → Playwright 截图 → 通过 → 下一个
```

**组件规范**（硬性要求）：
```tsx
// ✅ Props 用 interface
interface AgentCardProps {
  name: string;
  model: string;
  selected: boolean;
  onClick: () => void;
}

// ✅ 三态处理
if (loading) return <Skeleton />;
if (error) return <Alert variant="destructive" action="重试" />;
if (empty) return <EmptyState icon="🤖" text="暂无数据" action="创建" />;
return <Card>...</Card>;
```

**AI 自审**：
```
"检查刚写的 AgentCard：
1. Props 都有 TypeScript 类型吗？
2. loading / empty / error 三态都有吗？
3. 颜色全是 Tailwind 类名吗（没有硬编码 style={{color:'#xxx'}}）？
4. 有 hover 反馈吗？
修完跑 npm run build 确认。"
```

**门控（每个组件）**：
- [ ] `npm run build` 零错误
- [ ] Props 有 TypeScript interface
- [ ] loading / empty / error 三态（如适用）
- [ ] 颜色全用 Tailwind 类名
- [ ] 行数 50-200
- [ ] Playwright 截图正常

## 阶段 4：联调 & E2E

**目标**：前端调通后端，核心用户流程端到端跑通。

```
1. 启动后端: python main.py
2. 启动前端: npm run dev
3. Playwright 执行核心流程:

[用户打开] → [选 Agent] → [输入消息] → [点发送] →
[看到流式回复] → [费用面板更新] → [消息出现在历史]
```

**AI 协作**：
```
"后端 localhost:8800，前端 localhost:5173。用 Playwright 执行核心流程:
1. 打开首页，确认 4 个算法卡片可见
2. 点"快速排序"，确认跳转到快排页面
3. 点"随机生成"再点"开始"，确认动画播放
4. 等动画结束，确认结果显示和步骤列表高亮正确
5. 检查 console 无报错
发现问题直接修。"
```

**门控**：核心流程 Playwright 通过 + 0 console 报错。

## 阶段 5：视觉打磨（截图闭环）

**目标**：从"能跑"到"好看"。**这是 AI 开发的标志性环节**。

```
循环（通常 3-5 轮）:
  AI 改样式 → Playwright 截图 → AI 自己看截图 → 判断问题 → 改 → 再截图
```

**检查清单**（AI 对着截图逐项核对）：

| 检查项 | 标准 |
|--------|------|
| 配色 | 全部在主题令牌内，无硬编码 `#` 色值 |
| 间距 | 同类元素 gap/padding 一致（4px 基准） |
| 字号层级 | 标题 > 正文 > 提示 > 标签，层级清晰 |
| 圆角 | 按钮 sm / 卡片 md / 弹窗 lg，不混用 |
| hover 反馈 | 所有可交互元素有视觉反馈 |
| 暗/亮主题 | 切换后颜色全部正确对应 |
| 响应式 | 1024px / 768px 布局不崩 |
| loading 态 | 有骨架屏或 spinner |
| empty 态 | 有引导文字 + 操作按钮 |
| error 态 | 有错误消息 + 重试按钮 |

**AI 协作**：
```
"Playwright 截图所有页面。对着 shadcn/ui 官网暗色主题组件对比。
按检查清单逐项核对。从最丑的组件开始修。每修一轮截图对比。"
```

**门控**：AI 自己对 10 项清单打勾通过。

## 阶段 6：验证门禁 & 部署

**目标**：确保没坏，上线。

### 6A. 全量检测

```bash
# 前端
npm run build && npm run lint

# 后端
find backend -name '*.py' -exec python -m py_compile {} \;
pytest tests/ -q

# 安全扫描
grep -rn 'api_key\s*=\s*"[^"]\+"' backend/   # 硬编码密钥 → 必须 0 结果
grep -rn '#[0-9a-fA-F]\{3,6\}' src/            # 硬编码颜色 → 应该很少或 0
grep -rn 'console\.log' src/                    # 调试代码 → 必须 0 结果
```

### 6B. 部署

```
前端:  git push → Vercel 自动 npm run build → 部署
后端:  git push → Railway/Fly.io 自动 Docker build → 部署
```

### 6C. 上线后

- [ ] 生产环境跑一次核心流程 Playwright
- [ ] 监控面板 OK（费用、错误率、延迟）
- [ ] 日志有输出、无异常堆栈

**门控**：生产环境 health check 200 + 核心流程 Playwright 通过。

## 防退化和教训（每次开发前扫一眼）

### 死循环预防（Doom Loop Prevention）

| 现象 | 应对 |
|------|------|
| AI 反复修同一个 bug 修不好 | **立即停**。新开对话，重新描述问题 |
| 上下文太长 AI 行为变怪 | `/compact` 或新开对话 |
| 一个功能超过 5 轮还没对 | 回到 Spec，确认范围没蔓延 |
| AI 一次生成超过 300 行 | 叫停，拆成更小批次 |

### 踩过的坑

| 错误 | 教训 |
|------|------|
| 不写 Spec 直接让 AI 写代码 | Spec 先行，文档驱动 |
| 技术栈选 AI 不擅长的 | React+TS+Tailwind+shadcn/ui |
| 一次让 AI 写 10 个文件 | 逐端点/逐组件，每个验证通过才继续 |
| 不做视觉验证 | Playwright 截图闭环 |
| 不用 AI 自审 | AI 平均能发现自身 2-3 个 bug |
| 数据库用 ALTER TABLE 热修 | 迁移脚本，可回滚 |
| 部署前不扫密钥/硬编码 | grep 扫描是最后一道防线 |

### 人审查清单（每次 Review AI 代码）

- [ ] 输入校验——所有外部输入在边界处校验？
- [ ] 错误处理——是否静默吞异常？
- [ ] N+1 查询——循环里有数据库调用？
- [ ] 硬编码密钥——有 `api_key = "sk-..."`？
- [ ] 硬编码颜色——CSS 里有 `#xxxxxx`？
- [ ] 缺失状态——loading / empty / error 三态？
- [ ] 调试代码——有 `console.log` / `print`？
